# Production Media Storage & Tigris Architecture

This document outlines the architecture, invariants, security controls, and lifecycle transitions for production image and media storage across Cafnet.

---

## 1. Architecture Overview

Cafnet uses **Tigris Object Storage** (S3-compatible, zero-egress, global strongly-consistent object storage) for all media assets (business covers, gallery photos, menu item photos).

### Direct-to-Storage Upload Flow

Image bytes never transit through the Render Go API servers. Instead, uploads occur directly from the browser to Tigris using short-lived (10-minute) presigned PUT URLs:

```
 Next.js (Browser)
       │
       │ 1. POST /api/v1/media/uploads (Target, MIME, Size)
       ▼
    Go API
       │
       │ 2. Authenticate + Authorize (ReBAC)
       │ 3. Validate MIME & File Size (<= 10MB, jpeg/png/webp)
       │ 4. Persist PENDING media record
       │ 5. Issue Tigris Presigned PUT URL
       ▼
 Next.js (Browser)
       │
       │ 6. Direct HTTP PUT image bytes to Tigris
       ▼
    Tigris Storage
       │
       │ 7. POST /api/v1/media/uploads/{id}/complete
       ▼
    Go API
       │
       │ 8. Authenticate + Authorize media ownership
       │ 9. HeadObject / ObjectExists on Tigris
       │ 10. Verify Content-Type & Size
       │ 11. Mark Media READY & link to target entity in PostgreSQL
       ▼
 PostgreSQL / UI
```

## 2. Deterministic Object Keys

Clients are never permitted to supply custom paths or filenames. All object keys are deterministically generated by the Go API:

| Target Type | Media Type | Object Key Format |
|---|---|---|
| Submission Cover | `BUSINESS_COVER` | `submissions/{submissionID}/cover/{mediaID}.{ext}` |
| Approved Business Cover | `BUSINESS_COVER` | `businesses/{businessID}/cover/{mediaID}.{ext}` |
| Approved Business Gallery | `BUSINESS_GALLERY` | `businesses/{businessID}/gallery/{mediaID}.{ext}` |
| Menu Item Photo | `MENU_ITEM` | `businesses/{businessID}/items/{itemID}/{mediaID}.{ext}` |

File extensions are derived strictly from the validated MIME type:
- `image/jpeg` -> `.jpg`
- `image/png` -> `.png`
- `image/webp` -> `.webp`

## 3. Storage Abstraction

The storage layer is decoupled behind the `ObjectStorage` interface (`backend/internal/storage/storage.go`):

```go
type ObjectStorage interface {
    CreatePresignedUpload(ctx context.Context, bucket, key, contentType string, expires time.Duration) (string, error)
    CreatePresignedDownload(ctx context.Context, bucket, key string, expires time.Duration) (string, error)
    DeleteObject(ctx context.Context, bucket, key string) error
    HeadObject(ctx context.Context, bucket, key string) (*ObjectInfo, error)
    ObjectExists(ctx context.Context, bucket, key string) (bool, error)
    CopyObject(ctx context.Context, srcBucket, srcKey, dstBucket, dstKey string) error
    PublicURL(bucket, key string) string
}
```

Implementations:
- `TigrisStorage` (`internal/storage/tigris.go`): Production implementation using AWS SDK v2 for S3 targeting Tigris endpoints.
- `MemoryStorage` (`internal/storage/memory.go`): Thread-safe in-memory mock for automated integration test suites without external network dependencies.

## 4. Lifecycle Transitions

### Stage 1: Before Business Approval (Submission Cover)
- When submitting a new business (`POST /api/v1/submissions`), the user must provide exactly one cover image.
- The image is uploaded as `target_type="submission"` before final submission.
- The user can preview, replace, or remove this cover image prior to finalizing the submission.
- Full gallery management is **disabled** prior to business approval.

### Stage 2: Business Approval Transition
- When an admin approves a submission (`POST /api/v1/admin/submissions/{id}/approve`):
  1. The canonical `businesses` record is created.
  2. The manager ownership relation is created in `business_managers`.
  3. The submission cover image (`media` record) transitions ownership to the new `business_id` as `BUSINESS_COVER` with `sort_order = 0`.
  4. The business record's `cover_image` URL and `cover_media_id` are populated.
- No re-uploading or redundant byte copying is required.

### Stage 3: After Business Approval (Manager Controls)
- Once approved, the business manager has full media capabilities:
  - **Cover Photo:** Replace cover photo at any time.
  - **Gallery:** Upload up to 20 gallery images (`BUSINESS_GALLERY`), delete photos, and reorder photos (`PUT /api/v1/businesses/{id}/media/gallery/reorder`).
  - **Set as Cover:** Elevate any gallery photo to the primary cover photo (`PUT /api/v1/businesses/{id}/media/cover`).
  - **Menu Items:** Upload, replace, or delete one photo per menu item (`target_type="menu_item"`, `DELETE /api/v1/menu/items/{id}/image`).

## 5. Security & Invariants

1. **Zero Credential Exposure:** Tigris access keys and secrets are never exposed to the frontend, browser, logs, or error responses.
2. **ReBAC Authorization:** All media mutations enforce strict ReBAC checks. Only verified business managers can upload or modify media for their business.
3. **MIME & Size Enforcement:**
   - Supported MIME types: `image/jpeg`, `image/png`, `image/webp`.
   - Executable files, SVGs, scripts, and arbitrary binaries are strictly rejected.
   - Max file size: 10 MB per image.
4. **Verification on Completion:** An upload is never marked `READY` based solely on client assertion. The backend authoritatively inspects the Tigris object via `HeadObject` and verifies its existence and size.
5. **Neutral Placeholders:** Missing images fall back to the neutral Cafnet placeholder (`/images/cafnet-placeholder.svg`). Stock/mock imagery is never used for missing content.

---

## 6. Cleanup Strategy for Rejected or Orphaned Submissions

- When a business submission is rejected:
  1. The submission status is set to `REJECTED`.
  2. The associated media record status is updated to `FAILED` or soft-deleted, preventing it from ever surfacing publicly.
- **Orphan / Incomplete Uploads:** Any upload that remains in `PENDING` status past the presigned URL expiration (10 minutes) is considered orphaned.
- A scheduled background cleanup task or Tigris lifecycle policy removes objects matching `submissions/*` that are associated with rejected submissions or uncompleted uploads older than 7 days.
